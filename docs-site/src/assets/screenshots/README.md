# Documentation screenshots

Captured from a running `quickstart/sqe` stack by the `capture` Playwright
project, which runs the same use-case definitions the test suite runs:

```sh
make docs-screenshots
```

Every image here is produced by a step in `frontend/e2e/usecases/definitions/`,
and `manifest.json` records which step produced which file. The pages under
`guides/use-cases/` are generated from that manifest, so a screenshot cannot
appear in the manual unless a test actually reached that screen.

**Not** part of `make docs-build`. It needs a live stack, so it cannot run in CI.
`check-screenshot-refs.mjs` does run in CI, and fails the build if a page
references a missing image or an image is referenced by nothing.

## Before committing one

- Look at what it actually captured. A screenshot of a live stack can include
  more than intended: real usernames, workspace names, table contents.
- Images are served **verbatim**. The site uses Astro's passthrough image service
  because sharp is excluded on licence grounds (LGPL libvips), so there is no
  automatic resizing. The capture project pins 1440x900 for that reason.

## On how many screenshots to keep

An earlier version of this file advised that "a list page rarely earns one",
because every screenshot was hand-picked and hand-committed — an unbudgeted
maintenance cost that went stale silently.

That guidance is **deliberately superseded**. Images are now generated by the
tests that keep them honest, regenerated wholesale rather than patched, and the
reference check fails the build when an image and its page disagree. The marginal
cost of one more is close to zero, so capture the screens a reader needs rather
than rationing them.

What the check still cannot catch is a screenshot that is merely *out of date* —
a stale picture of a route that still exists. The answer to that is to re-run
capture wholesale, which takes well under a minute for the current registry.
